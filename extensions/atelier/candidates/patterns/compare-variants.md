# Compare alternatives on the same task

**Pick when:** the human must choose among builds, models, designs or implementations using comparable evidence.

**Hierarchy:** comparison question and shared conditions → same cases across alternatives → decisive
agreement/disagreement → inspect the actual outputs → adoption Decision with consequences. Put build,
criteria and input identities beside the comparison; name incomparable cells instead of implying a winner.

**Compose:** [run-matrix](../components/run-matrix/README.md) for aligned outcomes;
[claim-card](../components/claim-card/README.md) for each hands-on probe;
[observation-stamp](../components/observation-stamp/README.md) for measured identities.
Add [review-bridge](../components/review-bridge/README.md) only if marking inside controlled apps is in scope.
A matrix can compare text results without any bridge or screenshots.

**Why:** Thomas compared identical questions across builds in a C/K matrix (ME T7). Another report had
no links to the apps, and rebuilding at current HEAD would silently change its numbers (WC T2/T3, S L61).
“Side by side without a comparison → one at a time” permits simultaneous views here, not everywhere
([VV line 26](../SOURCES.md)). WC's four-app judging and anonymous ordering were not owner-validated.

**Does not fit:** a queue of unrelated outputs, different criteria disguised as equal tests, or media review
where only the latest version matters. Blind order and cost reveal need task-specific agreement.
