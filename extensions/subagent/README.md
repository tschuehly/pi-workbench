# Subagent extension

Level 1's attended `subagent` tool. One invocation accepts `task`, a bundled `profile`, a `cognitiveRole`, optional author provider or exact author model, optional reviewer `excludeFamilies`, an optional owner-requested `modelOverride: "<provider>/<model>"` exception, optional explicit `effort`, and an optional `background` flag; it resolves a fresh provider/model/effort binding through Workbench model-orchestration policy and delegates process lifecycle to `packages/pi-execution-adapter/`. A `review` or `light-review` model override must still come from a family other than the author's. The profile says what kind of work the child does; the Cognitive Role says how much it must decide and selects the model tier (see `skills/model-orchestration/SKILL.md`).

When `background` is omitted, the tool streams progress and blocks until the child finishes. Decision 99 makes `background: true` the system-prompt preference; foreground blocking is only for a result that is the lead's immediate next input when nothing useful can happen first. After a background launch, the lead finishes any genuinely independent work and ends the turn. The completion signal starts the next turn; the lead never calls collect to wait. When a background child reaches a terminal outcome, the extension sends one bounded `steer` signal at the next safe model boundary. The signal is composed when sent and carries the compact result and completion receipt of every pending child that fits 24,000 characters (the bulk-collect budget); its delivery marks exactly those children collected, so the lead needs no collect turn. Children that do not fit are named for one `subagent_collect` without an `executionId`; `subagent_status` is diagnostic. Further completions send nothing while the signal is outstanding; delivery of that exact message re-arms attention, and a child that finished after the signal was composed is signalled at that delivery, inside the same run, so a Worker reads it before it settles. Attention stays pending until that delivery or collection, so if Pi drops the queued signal, the next settled agent re-sends one coalesced signal (a dropped receipt-failure wake likewise). A delivered signal never re-fires, so there is no reminder loop. A terminal collection suppresses a not-yet-sent wakeup, re-arms it if collection detaches before delivering the result, and permanently handles it after reconciliation. Explicit cancellation and `session_shutdown` suppress late wakeups while cancelling live children. A `/reload` is the exception: it re-instantiates the extension in the same process, so the shutdown hands running and uncollected children, Worker dispatch locks, and pending completion attention to the next instance through a process-global keyed by session ID. The reloaded instance replays their roster rows, answers `subagent_status`, `subagent_collect`, `subagent_steer`, and `subagent_cancel` for them, and receives their completion signal once; adopted children keep the adapter code that launched them, while new launches use the reloaded revision. If no instance claims the handoff within 60 seconds, or the session ends first, the children are cancelled. Three companion tools reconcile backgrounded children within the same session: `subagent_status` (non-blocking diagnostic snapshot of one child or a list), `subagent_collect` (without an `executionId`, a bounded aggregate of every ready terminal-uncollected child; with one, an immediate bounded snapshot while running or while a finished Worker's receipt is settling, otherwise the compact terminal result), and `subagent_cancel` (cancel and confirm termination). Bulk collect reports and skips settling Workers; each receipt settlement sends the normal completion signal. Neither a running nor settling snapshot marks the child collected. Backgrounding is in-session only: children still die on `session_shutdown` and receive no durable identity, recovery, or unattended lifetime. The lead session records each child's launch, terminal outcome (bounded result, diagnostic, and child session), and collection as `pi-workbench.subagent-child` custom entries, so after an extension reload or session resume `subagent_status` and `subagent_collect` still answer for the same IDs: a terminal child returns its retained result, and a child that was live when the earlier runtime ended reports `interrupted`. Nothing is resumed or relaunched. Durable, unattended background execution remains deferred to the controller.

`subagent_steer` sends the lead's message into a running Subagent or Worker as an RPC `prompt` with `streamingBehavior` `steer` (after the child's current tool calls) or `followUp` (once it would otherwise stop). It fails for a child that has not received its assignment or has finished. With `requestUpdate: true` it appends an instruction to call `report_status`; the child's first self-report after acceptance wakes the lead once with a bounded `pi-workbench:child-update` `steer` message that grants no authority. A child that ends without reporting sends only the normal completion signal. When a running child has not called `report_status` for 55 minutes since launch or its last report, the extension sends it the same update request on its own; that report wakes nobody, and only the child's next report re-arms the request, so at most one is pending. Terminal, cancelled, and session-ended children get none, and a reload keeps the original watcher instead of starting a second. This is best effort, not a guarantee: a long-running tool call, a hung model request, or a Worker held waiting for its leaves (`holdForLeaves`) delays the report. A coordinator Worker has `subagent_steer` too and steers its own leaves the same way; the lead cannot reach those leaves directly. Children cannot start a question to their parent mid-run. Inside a Worker, background leaves are allowed: the Worker holds settlement at `agent_before_settle` until they end, then continues once per uncollected leaf so its dispatch never returns while a leaf is still writing.

Bundled profiles are `scout`, `planner`, `reviewer`, `implementer`, and `plain`; `plain` has the implementer's tools but adds no profile-specific instruction. Every profile receives the shared assignment wrapper and can call `report_status` at material phase changes, in the same tool batch as its next real tool call; the roster already shows the latest tool call, a lone report's result reminds the child to let the next one ride along, and the roster labels missing reports honestly. Every profile also receives `compact_and_continue`: the adapter treats the settle an accepted checkpoint causes as a pause (`compacting context` on the roster), and the child's result is its final message after the resumed run. Children keep native foreground bash and have no Monitor, so the wrapper tells them to wait with one `wait-until` call (`wait-until.mjs`, linked onto Pi's PATH by `scripts/promote-installed`) instead of `sleep` or `tail -f` turns: it blocks silently until a file exists or has a line matching a regex, a PID exits, a command exits 0, or a URL answers 2xx, whichever comes first (exit 0, printing what held), or until `--timeout` (default 600 s; exit 124, printing each condition's last observation). Inside a child (`PI_WORKBENCH_EXECUTION_KIND` set) the timeout is capped at 3300 s and the exit-124 line says so, so the child reports and waits again; the wrapper also tells children to run long commands in the background and wait with `--pid`. The lead is not capped. Each condition polls on its own every `--every` seconds (default 5), so a slow command never delays the others; each command attempt runs in its own process group, which is killed when the attempt exits or the wait ends, and a guard in that group kills it within a second if `wait-until` itself dies, as when Pi aborts the bash call. A log is rescanned whenever it changes, so a rewritten log is read anew. The child's activity line reads `running wait-until`: the adapter names any executable installed in Pi's bin directory, at any command position, never its arguments. Profiles select child behavior and requested tools independently from the Cognitive Role used for model and Model Effort routing; any known role may be paired with any bundled profile. For `independent-judgment`, `challenge`, and `independent-review`, `independentOfModel` may always quote the exact author from a completion receipt: default routing classifies its underlying model family, while an active single-provider overlay uses the exact model to select a different allowed model. Gateway authors such as GitHub Copilot require an exact model; unknown families fail closed. Without either author parameter, routing defaults to the active parent model. For a distinct-family panel, pass already-selected reviewer families as `excludeFamilies`; the resolver selects a policy candidate outside both the author's family and those exclusions. Exclusions are rejected for ordinary roles and distinct-model overlays. Each independent review uses fresh subagent context; status and terminal adapter receipts retain its family evidence. Requested tools are intersected with the adapter's host ceiling. User/project profiles, static model fields, batches, chains, retries, transcript forks, and durable background execution that survives the session are intentionally unsupported.

A child result is a bounded summary. The child is told its budget in its prompt (`PI_WORKBENCH_RESULT_MAX_CHARS`, default 8,000 characters); a longer final message is cut, the full text is written to `~/.pi-workbench/results/<executionId>.md` (`PI_WORKBENCH_RESULTS_DIR`) and the truncation note names that path and the child session. Bulk `subagent_collect` and the completion signal count truncated results as "verification incomplete"; the lead reads the full text with offsets or requests a bounded follow-up instead of rerunning the task.

Four worker tools add durable attended workers beside the ephemeral subagent, per [`docs/plans/level-1-durable-workers.md`](../../docs/plans/level-1-durable-workers.md). `worker_create` records a machine-local identity (owning lead session, name, one semantic scope, bundled profile, bound repository root) in `packages/worker-registry/` and starts no process. `worker_dispatch` runs one bounded attended assignment with the same lifecycle as `subagent`, resuming the worker's persisted Pi session for continuity. Each dispatch resolves a fresh binding by Cognitive Role; like `subagent`, it accepts an optional owner-requested `modelOverride: "<provider>/<model>"` and optional explicit `effort`, with fail-closed effort, catalog, mapped-quota, and overlay checks. Independence roles are rejected because independence requires fresh context. One dispatch at a time per worker: a busy worker fails preflight, terminal outcomes release the lock before any completion signal is sent, a background receipt-settlement failure emits separately deduplicated bounded per-execution `outcome_unknown` attention that never merges with or clears the coalesced signal and claims no lock release, while a foreground failure returns an `outcome_unknown` tool result with the child result marked inspection-only, and `subagent_collect` holds a background Worker result until its receipt settles so the same failure collects as `outcome_unknown` rather than as a success, an `outcome_unknown` dispatch requires `acknowledgeInspection` before the next one, and a dead lock owner is reclaimed only after liveness verification. Workers require and are owned by the persisted lead Pi session that creates them: dispatch and retirement reject foreign sessions (including forks and new sessions), while the first mutation claims a legacy unowned record, and `worker_status` lists only that session's active workers by default. `worker_status { all: true }` exposes all machine-local records, including retired and foreign-session workers, for diagnostics. Worker identity survives reloads and process restarts of its owning persisted session; execution never survives session shutdown, and no Run authority or managed recovery is implied.

The child uses a fresh, machine-local persistent Pi RPC session (or the worker's resumed session). In interactive Pi, `⌘B` (or `Ctrl+Alt+B`) moves the newest foreground Subagent or Worker into the background without cancelling it, using the same coalesced completion signal and reconciliation flow as `background: true`; `⌘B` requires a terminal that forwards the Command/Super modifier. Every active dispatch publishes to the shared **Active** surface above the editor. Width-aware, single-line pills pack horizontally and wrap as units. Each pill leads with mechanically normalized current activity, protects model and Model Effort metadata, and adds compact `🤖` Subagent or `🧰` Worker identity and Cognitive Role when width permits; the launch objective is omitted. Foreground pills disappear when execution ends. A background pill remains terminal and uncollected until the completion signal carrying its result is delivered, `subagent_collect` reconciles it, or `subagent_cancel` removes it. While the parent waits, the foreground tool additionally renders a bounded rolling activity log with elapsed time, recent normalized lifecycle/tool events, and a periodic last-activity refresh. Raw thinking content is never shown. Cancellation is confirmed through process termination, and the parent receives only the compact terminal result and session metadata. This grants no managed Run authority, durable actor identity, workspace isolation, recovery, acceptance, or publication right.
