# Vercel Deepsec as risk-triggered security verification

## Scope and evidence basis

This note evaluates Deepsec only as a security-verification capability inside the Pi Workbench implementation loop. It does not evaluate Deepsec's onboarding experience or propose adopting its lifecycle. The inspected source is Vercel Labs Deepsec package `2.3.4` at commit [`9722127bff6b36cc5ff4fe2e941dbf40822fe044`](https://github.com/vercel-labs/deepsec/tree/9722127bff6b36cc5ff4fe2e941dbf40822fe044); the first-party product announcement is Vercel's [2026-08-10 changelog](https://vercel.com/changelog/simplified-onboarding-for-deepsec).

Evidence labels used below:

- **Observed implementation** — behavior directly present in the pinned source.
- **Tested behavior** — behavior asserted by tests in that source; this review did not independently prove model quality.
- **Upstream claim** — first-party prose not established by the inspected implementation or tests.
- **Unknown** — requires a bounded Workbench experiment or additional evidence.

Deepsec calls each `scan`, `process`, or `revalidate` invocation a “run.” In this note, those are **Deepsec processing records**, not Workbench **Runs**. They grant no authority and cannot advance the Controller Lifecycle.

## Relevant mechanism

### Change-scoped processing

**Observed implementation.** Direct mode accepts exactly one of `--diff`, `--diff-staged`, `--diff-working`, `--files`, or `--files-from`. It obtains names with `git diff --name-only --diff-filter=AMRC`, normalizes and deduplicates paths, rejects paths outside the project root, drops missing files, and applies default ignores. It then scans and AI-investigates every retained file, including files with no regex match. The model receives whole files and may follow relevant imports; this is file-scoped review, not patch-hunk review. Deleted files are not reviewed. Tests cover changed/added file selection, mutual exclusion, ignores, traversal rejection, missing files, and deduplication. ([implementation](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/deepsec/src/file-sources.ts), [tests](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/deepsec/src/__tests__/file-sources.test.ts))

**Observed implementation and tested behavior.** The scoped scanner writes a `FileRecord` even when no matcher fires, preserving regex candidates only as prompt signals. The processor's direct path bypasses ordinary pending/error filtering and investigates the requested records again. Findings are merged by vulnerability slug plus normalized title, and only findings first produced by the current Deepsec processing record count as net-new. PR-comment tests verify that older and unattributed findings are excluded. ([scanner and tests](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/scanner/src/__tests__/scan-files.test.ts), [processor](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/index.ts), [comment tests](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/deepsec/src/__tests__/pr-comment.test.ts))

This shape is potentially useful after a risk-bearing implementation mutation: Workbench can provide an exact changed-file list, and Deepsec can perform a fresh holistic security read without first requiring a whole-repository scan. It is not sufficient for changes whose security consequence lies in deletion, configuration outside the retained set, generated artifacts, or interactions that require runtime evidence. The default ignore policy also excludes tests and distribution output; a risk classifier must decide explicitly whether `--no-ignore` or a curated `--files-from` list is required rather than accepting that default silently. ([direct-mode documentation](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/docs/reviewing-changes.md))

### Pi backend and security boundary

**Observed implementation.** Deepsec `2.3.4` includes a Pi backend using `@earendil-works/pi-coding-agent` `0.81.1`. It constructs an in-memory Pi `AgentSession` with only `read`, `grep`, `find`, and `ls`; disables extensions, skills, prompt templates, themes, context files, compaction, and images; and appends a static-source-only instruction. Custom tool operations enforce lexical and real-path containment under the project root, including symlink resolution. The model session has no shell or write tool. Tests establish in-root reads, rejection of an outside read, local `find`, gateway resolution, and direct-provider precedence. ([package](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/deepsec/package.json), [Pi backend](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/agents/pi-sdk.ts), [Pi tests](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/__tests__/pi-sdk-tools.test.ts))

That is narrower than the README's general warning to treat Deepsec like a coding agent with full shell access. The warning remains relevant to the host CLI, other backends, setup/install, dynamically loaded `deepsec.config.*`, and plugins; it is not an accurate description of the pinned Pi investigation session's tool set. Deepsec is designed for trusted source, while repository text and `INFO.md` enter the model prompt. The Pi boundary limits model tools but does not prevent source from being transmitted to the selected provider, make model output trustworthy, or sandbox the host Node process. ([README security model](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/README.md), [config-loading architecture](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/docs/architecture.md))

**Workbench implication.** Any experiment must force `--agent pi`; Codex and Claude backends are out of bounds because Pi is the only Workbench model-worker harness. The invocation remains an attended, bounded Pi capability. Deepsec's internal session and processing records are evidence-producing implementation details, not a Worker, Subagent, Dispatch, Episode, Workstream, or Workbench Run. No Deepsec action may mutate canonical Workstream or Run state, land a workspace, authorize remediation, establish Acceptance, or perform Publication.

### State, failure behavior, and cost

**Observed implementation.** Deepsec persists project registrations, per-file candidates/findings/history, processing metadata, refusal reports, costs, tokens, and debug output under a configurable data root. File processing uses statuses and per-file locks; graceful shutdown marks processing metadata erroneous, dead local PIDs and stale locks support reclamation, and a project-level atomic-directory mutex protects selection and claim. Tests cover lock ownership, dead-process recovery, generated-project repair, per-finding salvage, and refusal persistence. ([state implementation](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/core/src/run.ts), [state types](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/core/src/types.ts), [processor tests](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/__tests__/process-revalidate.test.ts), [core tests](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/core/src/__tests__/run.test.ts))

For Workbench, all of that is **machine-local generated state**, not authoritative Run state or durable project knowledge. `DEEPSEC_DATA_ROOT` can place it outside the target repository. This matters because records can contain absolute repository paths, source-derived findings, model/provider metadata, refusal text, and raw parse-failure output. Only selected evidence should be referenced from a Review Surface; no credentials, generated state, or Deepsec installation should be committed. ([data-root implementation](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/core/src/paths.ts), [data layout](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/docs/data-layout.md))

**Observed implementation.** Pi investigation retries transient failures up to three attempts, treats quota exhaustion as non-transient, stops launching new batches after quota or a completed-batch cost boundary, requests bounded JSON/field repair, records detected refusals, and fails loudly when no usable result remains. Processor tests verify cost allocation, bounded stop behavior, quota cancellation, and releasing unattempted claims. ([failure handling](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/agents/shared.ts), [Pi retries and repairs](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/agents/pi-sdk.ts), [processor tests](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/__tests__/process-revalidate.test.ts))

Two failure semantics are unsafe to consume without an adapter:

1. The direct-mode documentation says exit `1` means findings and other nonzero codes mean runtime errors, but the CLI explicitly exits `1` for findings, errored batches, and quota exhaustion. A Workbench caller must parse the structured result/state or output category; exit code alone cannot distinguish a security finding from an incomplete verification. ([documentation](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/docs/reviewing-changes.md), [CLI implementation](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/deepsec/src/commands/process.ts))
2. The models documentation claims refused files stay `pending` and therefore produce no false negatives. In the inspected Pi path, a refusal is collected after parse and returned with results; the processor appends it to history and marks returned files `analyzed`. The test establishes refusal persistence, not the stronger pending/no-false-negative claim. Treat any refusal or missing refusal report as incomplete evidence requiring a bounded alternate verification, not as a clean result. ([upstream claim](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/docs/models.md), [processor path](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/index.ts), [test](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/__tests__/process-revalidate.test.ts))

**Upstream claim.** Deepsec optimizes for strong models at high effort, and its README warns that large full scans can cost thousands or tens of thousands of dollars. Direct mode charges for each investigated file; revalidation is described as comparably expensive. The Pi default is `zai/glm-5.2` at `xhigh`, though agent, model, thinking level, concurrency, and batch size are configurable. ([README](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/README.md), [models](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/docs/models.md), [direct-mode cost note](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/docs/reviewing-changes.md))

The processor library's `maxCostUsd` is checked only after completed batches and can overshoot, especially with concurrency. The inspected `process` CLI command does not expose or forward that parameter in direct mode. Therefore the initial Workbench bound must be an exact small file list, finite batch/concurrency settings, an external deadline, and an owner-approved model/effort budget—not an assumed hard dollar ceiling. Actual Pi-backend cost, latency, false-positive rate, and marginal value are **unknown** until measured on Workbench changes. ([processor cost boundary](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/processor/src/index.ts), [CLI options path](https://github.com/vercel-labs/deepsec/blob/9722127bff6b36cc5ff4fe2e941dbf40822fe044/packages/deepsec/src/commands/process.ts))

## Fit with the Workbench quality loop

Deepsec fits only as a **risk-triggered verification capability**, not a universal phase or continuous gate. The Current Quality Loop evidence allows security review when repository policy, task risk, impact, reversibility, and evidence needs warrant it. Deepsec can contribute Primary Evidence and model Judgment about changed code, but its findings are claims until reconciled against source and other verification. Its local processing history is not an Episode, ledger, Judgment Dossier, or Acceptance record.

A candidate trigger should be narrow and source-backed: changed authentication or authorization boundaries; tenant isolation; secret, token, or session handling; untrusted parsing, redirects, uploads, filesystem/process execution, model/tool boundaries, network egress, cryptography, CI permissions, or externally exposed handlers; or an explicitly security-sensitive repository policy. Routine low-impact changes should not pay the cost or attention burden.

A bounded experiment should:

1. Invoke pinned Deepsec `2.3.4` with `--agent pi` against an exact reviewed `--files-from` list derived from the realized mutation, including relevant tests/configuration deliberately rather than relying on default ignores.
2. Keep `DEEPSEC_DATA_ROOT`, credentials, provider state, Pi state, and all generated findings machine-local; permit only source-reading Pi tools and the selected model endpoint.
3. Record package commit, model/provider, Model Effort, file list, diff base, ignore decision, elapsed time, usage/cost, failures, refusals, and produced finding IDs as provenance-bearing evidence.
4. Fail closed on runtime error, quota stop, malformed/incomplete output, refusal, missing expected file, or unknown outcome. Do not equate “no net-new findings” with proof of security.
5. Give every net-new finding one bounded disposition: **confirmed and remediated**, **false positive with source evidence**, **accepted residual risk by the owner**, or **deferred as a Material Question with an explicit next action**. Use revalidation only when it is the shortest safe route to disposition; do not loop until models stop producing findings.
6. Stop after the declared file set and disposition budget. Return the evidence to the lead Pi for synthesis into the Review Surface; any code change requires separately authorized implementation and ordinary verification.

## Recommendation: experiment, do not adopt

Run a small attended experiment on one or two genuinely security-sensitive implementation changes. Preserve the **Pi-only runtime**, keep Deepsec generated state **machine-local**, and treat Deepsec as a non-authoritative evidence producer with **no Workbench Run authority**. Require explicit, bounded finding disposition before the verification work closes.

Do not adopt Deepsec as a default gate or lifecycle component yet. Adoption evidence is missing for Pi-backend detection quality, false-positive burden, prompt-injection resilience, provider data handling, cost/latency under realistic Workbench diffs, deleted-file and ignored-file gaps, and reliable machine-readable separation of findings from incomplete execution. The refusal-state contradiction and overloaded exit code require an adapter or upstream correction before even experimental results can be consumed mechanically.
