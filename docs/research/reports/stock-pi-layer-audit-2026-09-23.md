# Pi Workbench over stock Pi: subtraction audit

**Verdict:** the main excess is *ambient scope*, not the Workstream Store. A fresh lead's persisted pre-filter prompt lists 39 skills and 32 tools; the checkout's Working Mode should reduce that TUI skill catalog to **27** entries if its exact-match filter succeeds. Further request-time instructions come from global packages. Stock Pi starts with four tools and loads skill bodies on demand. Test task-specific tool and skill exposure before changing installation policy; do not remove Workstream data or cut over the graphical client on this audit.

**Decision status:** recommendations, not approved changes to runtime policy, installed packages, Workstreams, or the graphical product. An Opus 5.5 advisor recommended scoped loading and preserving enforced safeguards; a fresh, cross-family Opus 5.5 review challenged this report. Its objections and disposition are recorded below. Only this report and its file index were added.

## Model-release and instruction-deletion eval (proposed, not run)

Start without a new `evals/` service; the [existing model-role evaluation plan](../../plans/model-role-evaluation.md) defines paired assignments and evidence fields, though it incorrectly says `plain` is absent. **Instrument gate:** the repository's agent-audit tests assume Pi 0.84.3 in its unpinned local dependency while both installed/local Pi are 0.87.1; repair and rerun the provider-input fixture against the selected Pi version before treating it as a wire recorder. Consent to exact request capture explicitly, keep secrets out, and clean captures afterward.

**Pre-register a bounded screen, not a benchmark verdict:** choose **12 frozen cases**, three each for simple in-repo coding, bounded evidence gathering, child lifecycle/collection, and a security/independence negative control. For each case freeze input, Git SHA, package/skill manifest and versions, tool/schema and prompt hashes, acceptance criterion, model/effort, timeout and quota window. Compare current versus *one* reduced load on the same model in isolated fresh sessions, alternating order: at most **24 trials**, plus at most **four** stock-Pi trials on the subset of simple tasks all arms can actually perform (**28 total**). A stock-Pi arm must disclose omitted Workbench functions; the required telemetry extension still loads. Budget cap before launch: at most **28 child processes** and **two hours wall clock**, with a smaller pilot allowed; stop on provider quota below **10%**, any uncontrolled filesystem mutation, or the wall-clock cap. These caps do not promise all coding cases complete within the budget. Do not run this as an unattended live-policy modification.

Before results, make one independent mechanical check for each case; blind semantic reviewers to arm/model. Screen exit: **zero authority/security/independence failures** in either candidate or baseline; no candidate-only deterministic failure or additional material correction; a measured **≥15% median reduction in first-call uncached input tokens** (or another named pre-registered benefit), without a **>10% median elapsed-time increase**. Any negative control failure is a hard stop, not an average to trade away. This is a *screen threshold*, not statistical equivalence: if a baseline itself fails, repair the fixture rather than count candidate success. Log actual provider input/cache reads/writes, tool use, corrections, elapsed time, quota and rollback step. Removing unused tools from a single task proves nothing about tasks that need them.

For a new model, hold the harness fixed and pair candidate vs incumbent first; then test *one instruction ablation within each model separately*. Do not mix changed model and changed prompt in a single comparison. The existing plan estimates roughly **30–40 comparable pairs** for a moderate quality difference; that is a **separately authorized larger campaign**, not included in the 28-trial cap. Inconclusive or quota-limited means no policy change. Deterministic checks outrank model judges, and any proposed binding/instruction change still needs owner review, independent challenge, preserved cross-family review, fail-closed quota routing and Checking floors. A stronger model may need fewer procedural reminders; it does not change security or state authority.
