What this is about

Right now Pi describes a session with one number: Operating Level 1 to 4. Level 1 is you and one Pi, watching everything. Level 4 is a controller running work while you sleep. Only Level 1 is built.

The number hides what actually differs. An overnight run on 8 August was treated as roughly Level 4. It had no controller, no crash recovery, no isolated workspace and no spending limit. It produced nothing, then reported itself complete.

The proposal: drop the single rank. Describe a session by the facts that vary — how closely you watch, who enforces rules, whether work survives a crash, whether the workspace is isolated, what the spending limits are. Each fact records whether it was asked for or actually granted.

Background — the four events these cards keep referring to

The failed AFK run, 8 August 2026. AFK means away from keyboard: an unattended overnight run. This one was supposed to produce a finished marketing video for the PhotoQuest project. A startup command was rejected before any real work began. Instead of stopping, the run kept diagnosing itself, and then reported the whole job as complete although nothing had been produced. It is cited constantly because it is the concrete proof that a model checking its own completion produces false “done” signals. docs/research/reports/afk-autopilot-production-failure-2026-08-08.md

The observer session. A second Pi session was watching that run. Rather than reacting only to real events, it woke on nearly every log line, spent about 25.9 million tokens and roughly $7, and initially repeated the failing run's own false success claim instead of challenging it. It is the standing argument for watching with deterministic events rather than a model.

PhotoQuest attempt 04. The proposed fourth unattended production attempt for the same pipeline. Attempt 03 also failed, with a step called Asset Scout hanging for fifteen minutes before being killed. Attempt 04 is deliberately blocked until that hang is reproduced and diagnosed outside production. Card D14 keeps it blocked.

The grill itself. A grill is an adversarial review: a lead session and a separately-modelled advisor argue a proposal across several rounds, then independent auditors check the result before a human rules on it. This one ran four design rounds and two closing audits. The first audit found six material gaps, all reconciled; the second found none. The advisor ran on a different model family from the lead, which is why its dissent is preserved on the cards rather than smoothed away.

Glossary — terms used on the cards
Operating Level 1–4
The current single-number description of a session. 1 Pair: you and one Pi, watching continuously. 2 Agree: you agree a written plan first. 3 Contract: work runs against an approved plan with independent review. 4 Manage: a controller runs execution so you can be offline. Only Level 1 is built.
Run
One durable pursuit of a stated outcome under agreed rules. Survives across sessions. Not built yet at V1.
Workstream
A personal container that tracks related sessions, links and open questions so you can pick attention back up later. Grants no permissions.
Subagent
A fresh, single-use Pi spun up for one bounded task, then gone.
Durable Worker
A helper Pi that keeps its context across several assignments within one scope, unlike a single-use Subagent.
Independence / cross-family routing
Having a check performed by something not anchored to the work under review — in practice, a different model family from the one that produced it.
Fail-closed
When something is unverified or uncertain, block rather than proceed.
Attention
Your finite capacity for real judgement. The system is designed to spend it only where it changes an outcome.
Effect class
The category of real-world consequence a piece of work can have. Used to decide which rules apply: a read-only overnight scout and a run that publishes files should not face the same requirements.
Provenance stage
The five labels attached to any posture value: requested (someone asked), recommended (policy suggests), required (a check demands), admitted (a mechanism actually granted it), observed (a receipt says it happened).
Ratification
You approving something after the fact. Deliberately not the same as a mechanism granting it — this distinction is the point of card D2.
Standing context
The roughly 750 words of Workbench-owned instructions injected into every session's prompt. Card D17 audits it.
Compaction
Summarising a session's context to free space, at a point where the summary will not lose something load-bearing.
Entry Preset
An optional named starting bundle of settings. It cannot grant a capability the system does not enforce. This is what you approved on 25 August.
Learning Candidate
An evidence-backed lesson from a run, proposed for promotion into permanent project knowledge.
FirstMate / coordination mate
A proposed assistant that helps you triage and resume your Workstreams without owning any of the underlying state. Card D11 scopes it down to notify-and-focus only.
Principle 14
Every material claim must be checked by an actor that did not produce it, with evidence rather than confidence. Card D15 keeps this as an unwaivable floor.
Decisions 79–82
The recorded decisions that establish the Level ladder as concepts rather than a roadmap (79), restrict V1 to Level 1 (80), allow model choice to vary by role (81), and forbid a UI level-switcher (82). These are what card D7 would supersede in round 2.

D1Nine fields with provenance, not a level number

Plainly: the core swap. Stop saying “this session is Level 3”. List the nine facts that actually differ instead, each marked as asked-for or actually-granted. The example below writes the failed August run out this way, and the mismatch the label hid becomes obvious.

Deciding: whether a Run's posture is described by fields whose values carry provenance, with per-field validity predicates, instead of one ladder rank.

➡ Recommend: accept.

Concrete example — the failed AFK run as a vector
attention:    outcome-only        (requested)
governance:   session-owned       (observed — no controller)
durability:   live-session-only   (observed — crash = total loss)
workspace:    shared checkout     (observed — no isolation)
bounds:       unlimited turns     (observed — pi-goal default)
verification: dual judgment       (requested, ran)
“Level 4-ish” hid exactly this mismatch — the production failure report's conclusion (“the operating level did not match the use”) is this table. The ladder also has a live counterexample: durable workers put session-resumable durability inside Level 1 while Independence roles refuse continuity.

Validity is checked per field — admits(required, granted), conforms(admitted, observed) — not by ordering, because bounds order backwards and authority values are sets. Presentation stays simple: you request attention, commitment, and bounds; the environment supplies governance, durability, and workspace protection.

D2The provenance pipeline

Plainly: each fact is labelled with how real it is: asked for, suggested, demanded, actually granted, or observed. The point is that your approval never counts as granted — only a mechanism does. The August run treated “the human approved the plan” as granted authority and escalated itself on the strength of it.

Deciding: whether every field value carries one of five stages: requested → recommended → required → admitted → observed. A value is admitted only when a mechanism grants it; your approval is ratification — a recorded event, never an admitted stage.

➡ Recommend: accept.

Concrete example — a worker dispatch today
Role requested → binding recommended by routing policy → cross-family required for Independence → binding admitted only after the adapter verifies the launched runtime (Decision 88, fail-closed) → receipt records what observed.

In the AFK run, “the human approved the plan” was treated like granted authority; that ambiguity let escalate route into more autonomous work. Ratification semantics stay deferred (Deferred Design Decision 7) — this proposal does not settle them.

D3Three constraint classes, applied per effect class

Plainly: rules come in three strengths — never break, this repository requires it, advice you may skip with a reason. Which ones apply depends on what the work can affect. A read-only overnight scout and a run that publishes files should not face the same checklist.

Deciding: whether constraints divide into universal invariants / binding repository requirements / ignorable-with-reason recommendations — evaluated per effect class.

➡ Recommend: accept.

One of each, plus why effect classes matter
  • Invariant: the invoked plan never owns completion semantics — the missing clause that let the PhotoQuest plan call goal_complete with Steps 4–8 unfinished.
  • Repository requirement: PhotoQuest's browser-evidence rule.
  • Recommendation: “use two judges on this refactor.”
An overnight read-only scout needs budgets and an external completion predicate but no worktree isolation; the same posture shipping video files needs both. One global floor forced the wrong answer for one of them.

D4Commitment per object

Plainly: “we agreed the plan” is too coarse. Split it into four: the outcome, how you know it is done, constraints on the approach, and the exact route. Then conflicts settle themselves. If your prompt says “don't pause” and the plan says “stop at this gate”, the gate wins, because you agreed to it.

Deciding: whether direction commitment is four independently agreed, versioned objects — outcome, acceptance criteria, strategy constraints, implementation route — rather than one agreement altitude.

➡ Recommend: accept.

Concrete example — the AFK run's two recorded conflicts
Under D4: outcome and acceptance agreed; strategy adaptive, not a promise; route unagreed. The conflicts then resolve mechanically:
  • Prompt said “don't pause,” plan said “gate hard” (session-ledger F3). The gate is part of agreed acceptance, so it wins — not because plans beat prompts, but because that clause carries agreement and the prompt line does not.
  • You type “2 videos is fine” mid-run: a human amendment within authority re-versions the outcome object. Document type is irrelevant.
