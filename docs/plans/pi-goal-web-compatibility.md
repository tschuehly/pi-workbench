# Pi Goal web compatibility

**Current:** Upstream pi-goal publishes bounded Goal status and durable lifecycle messages; PI WEB consumes the RPC status and places a compact status chip beside the composer. These are presentation projections, not PI WEB authority over Goal state. A lifecycle card is a separate consumer concern; the cited PI WEB status commits do not establish that a lifecycle renderer shipped.

## Implemented upstream (`narumiruna/pi-extensions/packages/pi-goal`)

- [`dc0a00ca`](https://github.com/narumiruna/pi-extensions/commit/dc0a00ca) introduced the versioned status snapshot; [`c7ff5c9e`](https://github.com/narumiruna/pi-extensions/commit/c7ff5c9e) restricted JSON publication to RPC mode. `setStatus("goal", ...)` in RPC mode contains **exactly** `schemaVersion: 1`, `goalId`, `state`, and `objective`. The objective is a normalized, bounded **summary**, not the full Goal contract: 1–240 Unicode code points; the ID is 1–128; serialized status is at most 2,048 UTF-8 bytes. States are `active`, `waiting`, `paused`, `blocked`, `usage_limited`, and `budget_limited`. Waiting derives from active Goal state plus waiting metadata. Completion and clear remove the status key; transient `complete` is not a status snapshot. TUI (and normally unavailable print/JSON UI status) stays bounded, human-readable activity text; waiting and stopped statuses include bounded reason when available and `/goal status` / `/goal resume` guidance, not RPC JSON or the full objective. See [`runtime.ts`](https://github.com/narumiruna/pi-extensions/blob/c7ff5c9e/packages/pi-goal/src/runtime.ts) and [README status contract](https://github.com/narumiruna/pi-extensions/blob/c7ff5c9e/packages/pi-goal/README.md#public-status-contract).
- [`b1951ccf`](https://github.com/narumiruna/pi-extensions/commit/b1951ccf) added persistent visible custom messages (`customType: "pi-goal.lifecycle"`, `display: true`, `triggerTurn: false`); [`19908faa`](https://github.com/narumiruna/pi-extensions/commit/19908faa) hardened delivery/order and model-input handling. Schema-v1 `details` contains **exactly** required `schemaVersion: 1`, `goalId`, `transition`, `state`, with optional `reason` and/or `summary`; no objective or `eventId`. The persisted Pi session entry ID provides durable transcript identity and order; PI WEB still needs live/reload correlation and deduplication because a live custom `message_end` may arrive without `entryId`. ID: 1–128 Unicode code points; each optional normalized, terminal-control-free text: at most 400 code points; serialized details: at most 3,500 UTF-8 bytes. Transition → post-state: `start`/`resume` → `active`, `pause` → `paused`, `wait` → `waiting`, `block` → `blocked`, `usage_limit` → `usage_limited`, `budget_limit` → `budget_limited`, `complete` → `complete`, `clear` → `cleared`. The last two are **lifecycle post-states**, not status-snapshot values. Valid visible lifecycle messages are stripped from model input; their bounded fallback `content` starts `[pi-goal] automated lifecycle status, not a user instruction:` and includes available bounded reason/summary and relevant guidance, never the full objective. Malformed or unknown-version messages are not silently stripped. Passive restore/reload replays no lifecycle event; a newly detected restore-time transition emits once. Replacement/edit enqueue old-ID `clear` before new-ID transition, but Pi's void send API does not guarantee atomic persistence of the pair. See [`runtime.ts`](https://github.com/narumiruna/pi-extensions/blob/c7ff5c9e/packages/pi-goal/src/runtime.ts), [`lifecycle.ts`](https://github.com/narumiruna/pi-extensions/blob/c7ff5c9e/packages/pi-goal/src/lifecycle.ts), and [README lifecycle contract](https://github.com/narumiruna/pi-extensions/blob/c7ff5c9e/packages/pi-goal/README.md#visible-lifecycle-messages).
- [`c7ff5c9e`](https://github.com/narumiruna/pi-extensions/commit/c7ff5c9e) also persists terminal provider-retry exhaustion as an active **waiting** Goal without deadline, rather than transitioning the Goal to blocked state. Restore stays quiet and restores only any optional deadline timer; `/goal resume` or a follow-up can retry. The hidden `goal-contract` version 2 remains the model-visible full objective/rules/safety contract; it is independent of both presentation schema versions. See [README waiting/restore](https://github.com/narumiruna/pi-extensions/blob/c7ff5c9e/packages/pi-goal/README.md#external-waiting) and [`goal-contract.ts`](https://github.com/narumiruna/pi-extensions/blob/c7ff5c9e/packages/pi-goal/src/goal-contract.ts).

## PI WEB consumption and remaining boundary

- [`a1931d74`](https://github.com/tschuehly/pi-web/commit/a1931d74) adds the schema-v1 RPC status parser and current-status chip; at current HEAD, the parser accepts bounded non-JSON legacy text opaquely, while unparseable legacy status is hidden by the chip; [`0efc2b4d`](https://github.com/tschuehly/pi-web/commit/0efc2b4d) moves the chip beside the composer. Unsupported/malformed structured status is not partially trusted; free-text legacy status is not parsed into Goal fields. See [`extensionStatusSnapshots.ts`](https://github.com/tschuehly/pi-web/blob/0efc2b4d/src/client/src/extensionStatusSnapshots.ts), [`GoalStatusChip.ts`](https://github.com/tschuehly/pi-web/blob/0efc2b4d/src/client/src/components/GoalStatusChip.ts), and [`WorkbenchApp.ts`](https://github.com/tschuehly/pi-web/blob/0efc2b4d/src/client/src/components/WorkbenchApp.ts).
- **Remaining integration at these cited commits:** verify a schema-v1 lifecycle consumer/card independently of status: validate the exact details shape and bounds, design live/reload correlation and deduplication around the persisted Pi entry ID without assuming the live custom `message_end` carries `entryId` or adding an upstream `eventId`, render one accessible compact card in transcript order without generic SYSTEM duplication, and leave malformed/unknown versions to a safe bounded fallback. Do not infer that the status chip implements lifecycle rendering. Keep generic live and reload `display === true` filtering so hidden custom messages never cross the browser boundary; preserve visible `customType` and `details`. Keep successful transitions in transcript, actionable errors/rejections in notifications, and ordinary assistant output untouched. See PI WEB [`piSessionService.ts`](https://github.com/tschuehly/pi-web/blob/0efc2b4d/src/server/sessions/piSessionService.ts), [`transcriptMessages.ts`](https://github.com/tschuehly/pi-web/blob/0efc2b4d/src/server/sessions/transcriptMessages.ts), and [`chatMessages.ts`](https://github.com/tschuehly/pi-web/blob/0efc2b4d/src/client/src/chatMessages.ts).
- **Explicitly deferred:** migration of extension-generated start/resume prompts and the budget-wrap-up steer to hidden `pi-goal.trigger` messages, plus any TUI-emulation work. The existing hidden `goal-contract` must remain fully model-visible; do not claim all internal prompts have disappeared from owner transcript or model input. Managed-run RPC/controller expansion, Goal-specific endpoints, and browser-issued Goal commands are outside this attended Chat compatibility slice. PI WEB is a protocol client, not authoritative Goal state.

## Verification boundary

Upstream coverage now lives under `packages/pi-goal/test/` (not the formerly proposed `goal-runtime-smoke.mjs`); relevant files include `goal-status.test.ts`, `goal-lifecycle-message.test.ts`, and `goal-wait.test.ts`. PI WEB status tests are `src/client/src/extensionStatusSnapshots.test.ts` and `components/GoalStatusChip.test.ts`. For end-to-end acceptance, check blocked → `/goal resume` → reload: current RPC status, one ordered lifecycle entry if the consumer is present, no replay on passive restore, hidden contract absent from the UI but intact in model input, and no false claim that deferred trigger migration has removed internal prompt walls. These are acceptance checks, not a claim that the integrated flow was run here.
