The child later completed and reported the source-of-truth activity and collection rules; no status was fabricated by the browser fixture for this read.

A subsequent durable coordinator Worker ran **two** read-only dispatches in this scope. During each dispatch, the same status GET and owned `delegates(status)` parser returned one running `worker` row with the dispatched `coordination` role, actual `openai-codex/gpt-6-sol:high` binding and activity `subagent` (`terminal:false`). The Worker launched and collected one **foreground leaf Subagent** per dispatch; both leaf receipts were `openai-codex/gpt-6-luna:low`, successful. The second dispatch resumed the Worker's previous session and retained its scope context. The Worker registry recorded two successful dispatch receipts. After terminal collection the lead status GET returned `available:true` with zero active items. These checks did not install the client or alter/restart the live daemon; both Worker and leaf processes were read-only.

The leaf's focused command `node --test extensions/subagent/index.test.mjs` passed **38/38** tests at Workbench `9371221`, including mocked terminal retention, cancellation, Worker receipt/wakeup and nesting checks. A Worker cannot create another Worker; a leaf inside a Worker must run in the foreground. The coordinator Worker's own `report_status` tool was not exposed, so its activity came from observed execution rather than a self-report. A leaf did self-report once, but its separate session's activity was not fetched through the installed UI. The isolated browser acceptance covers two injected roster rows and inert untrusted text.

**Limits:** These reads prove actual running lead-visible Subagent and Worker bindings, successful Worker→leaf nesting and collection, but not a live terminal-uncollected row in the frontend, a cancelled live Worker/leaf, or completion wakeup after an interrupted receipt. Mocked adapter tests cannot replace those runtime cases or installed daily-use acceptance.
