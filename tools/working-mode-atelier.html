Alignment

Checking

Q1 · The missing behavior between Vibe and Plan

The common scale is the size of the unit you must understand before work continues—and how quickly you can judge it. Vibe keeps understanding continuous through chat. The missing behavior is lighter than a Plan: before one coherent change, Pi says what it intends and asks whether that is the right thing to do.

Vibe
Understand the next action continuously in chat.
Align
Judge one coherent change from a short summary.
Plan
Judge the concise direction for the whole task.
Spec
Judge required behavior and acceptance evidence.
Recommendation: use Alignment: Vibe | Align | Plan | Spec, ordered by the size of the agreement presented for human judgment. Vibe often pairs with continuous attention, but does not determine it; the restored Q13 decides how attention is expressed. These are interaction contracts, not mutation permissions.
What counts as one coherent change?

A change the owner can judge as one product, domain, architecture, or behavioral decision—for example, “replace the current showcase flow with a generic upload flow.” It is not each file edit, test, or mechanical implementation step. If Pi discovers another consequential choice, Align asks again.

Q2 · Does a durable plan file earn its complexity?

A file could give you a readable shared plan, let Pi check progress, and help a fresh session resume. It could also duplicate Workstream checkpoints, drift from the repository, and create confusion about whether mutable Markdown is authoritative.

Existing continuity

Pi session state preserves the active interaction. Workstream checkpoints already carry concise cross-session re-entry.

Potential missing surface

Neither gives owner and agent one continuously readable progress view outside the conversation.

Decision: no durable plan file. Keep accepted direction in session state and use concise Workstream checkpoints for fresh-session re-entry. This avoids a second mutable progress source.
What each choice commits

Experiment: one disposable task tests the idea before documentation changes. No file: rely on session state and Workstream checkpoints. Adopt now: make the file lifecycle part of Working Mode before usage evidence exists.

Q3 · Progressive disclosure for model orchestration

The current SKILL.md is 90 lines / 6.8 KB. Every invocation loads role classification, checking panels, quota resolution, launch guidance, and future controller rules. The proposal keeps one skill name but turns its short SKILL.md into a routing table that reads only the reference needed for this task.

Example 1 · You and Pi work directly without delegation in this task

No child model or independent review is needed, so load nothing from model orchestration. This is an example of the task shape, not a rule for Vibe, Align, Plan, or Spec.

Example 2 · Pi delegates bug reproduction

Load Binding only: classify the child as investigation, choose its model and Model Effort, and check quota. Do not load panel construction or managed-controller rules.

Example 3 · Checking is adversarial

Load Checking + Binding: decide how many independent challengers consequence requires, ensure different model families, then resolve each binding. Do not load managed Dispatch rules.

Example 4 · A future managed Run dispatches work

Load Managed dispatch for the Work Packet and controller boundary, plus Binding or Checking only when that Dispatch needs them.

Clarification from your decision: any Alignment value may use scouts, subagents, or Workers. The first child invocation triggers Binding. Alignment chooses the size of human agreement; it does not choose the execution shape.
Decision: one discoverable router, three conditional modules. A separate calibration reference loads only when we are evaluating whether the routing policy itself is good.

Q5 · What exactly triggers Align?

The alignment boundary must be lighter than a Plan without becoming vague. It occurs when investigation would turn an uncertain product, architecture, scope, or quality choice into durable implementation or parallel work.

Agent rule: ask when the next step would commit the repository, task scope, architecture, product behavior, quality trade-off, or parallel implementers to a direction the owner has not confirmed. Judge the semantic consequence—not whether a tool writes a file.
Ask before
  • A bug fix changes user-visible or API behavior.
  • A solution moves responsibility across modules or adds a dependency.
  • A local task expands into a workflow redesign.
  • Children would implement one still-open direction.
Proceed without asking
  • Read code, reproduce the bug, run tests, or gather evidence.
  • Use a scout or scratch prototype to investigate.
  • Edit, refactor, test, and document inside the confirmed change.
  • Repair a failure without changing the intended outcome or boundary.
Ask again when
  • Evidence contradicts the confirmed direction.
  • The user-visible outcome or architecture must change.
  • The affected scope expands materially.
  • The agreed checking or quality bar cannot be met.
Decision: Pi first summarizes the intended outcome, affected boundary, and checking. Confirmation covers the coherent change until one of the “ask again” conditions occurs. This is prompt-guided behavior with no mechanical mutation lock.
Trial status: re-evaluate after real use. Keep the rule if it catches consequential changes, leaves routine implementation uninterrupted, and produces summaries the owner can judge quickly. Revise it if asks are late, frequent, or ambiguous. Do not add mechanical enforcement before that evidence exists.

Q8 · What should Checking be before an explicit choice?

Checking means the minimum evidence Pi must produce before claiming the work is done. Alignment asks “are we changing the right thing?” Checking asks “what proves the result works?” A selected value is a floor; Pi may do more when the task warrants it.

Same example: Pi changes retry behavior after an API failure.

Checking: light

Inspect the diff and exercise the changed path once, then report what was observed. Automated tests are optional.

Checking: tests

Run the relevant automated test that proves retry count and failure behavior, then report the exact command and result.

Checking: adversarial

Run tests, then have an independent challenger look for missed failure modes or disagreement with the accepted behavior. Scale the panel to consequence.

The default decision

Start at light

Ordinary work has a visible minimum without forcing automated tests onto prose, research, or tasks that lack them.

Start at tests

Coding starts safer, but the default mismatches work where automated tests are not meaningful.

Start unset

The owner chooses after discovery, but every ordinary task gains a setup prompt.

Decision: there is no single repository-independent Checking default. Each repository may declare its default in a versioned Workbench config. The next round decides that file's location and first schema; precedence and missing-file behavior follow from those choices.
