# Owned Workbench protocol proof

This is an isolated protocol client, **not** the daily-use Workbench frontend. It selects registered projects, workspaces and existing sessions, creates a Chat with a single-flight/unknown-outcome lock, and displays paged history, in-flight assistant text and pending `ask_user` questions. Its native-textarea composer has per-window reload drafts and send/queue/stop protocol calls. Model and thinking selectors use each session's available values and server-confirmed status, and disable unavailable choices. While streaming, Send steers; the separate queue button keeps a follow-up for later. Server queue entries can be promoted or cleared, but queue mutation has only deterministic client tests so far. Confirm/select/input extension dialogs rehydrate from daemon status after reload and support answer/cancel; they do not survive a daemon restart. It supports bounded inline PNG/JPEG/GIF/WebP attachment selection (4 MiB total, 16 images), rejection without draft loss and real backend prompt acceptance. Staged image bytes stay in tab memory and are lost on reload or session switch; sent images enter session history. Persisted assistant thinking, tool calls and tool results are shown as structured, text-only blocks; untrusted HTML stays literal and image content appears as a placeholder, not a preview. The Workstreams panel lists and inspects snapshots through the active, revision-paired, workspace-scoped Workbench service. It shows confirmed checkpoints, Human Tasks and links as inert text and opens an associated Chat only when its complete local location and persisted session match the registered catalog. The panel can answer typed Human Tasks (yes/no, choice and free-text) against the inspected revision. It saves the exact append request before sending, reconciles uncertain outcomes using the Store's answer receipt, and allows only an exact idempotent retry until resolution. A stale revision requires a fresh review; unavailable browser storage blocks answering rather than risking an untracked retry. Workstream creation, checkpoint continuation, association repair, other mutations and automatic watch remain outstanding; manual refresh is available. The Worker/Subagent roster reads live session extension status, shows reported role/model/effort and running versus uncollected outcomes; missing or disconnected status is not treated as completed work. Markdown formatting, ad-hoc directory mapping, remote-machine picker, and general file attachment/delivery remain absent. Files lists registered local workspaces and opens bounded literal text; version-verified UTF-8 files can be edited and saved with a stale-write guard, while binary/truncated/unverified files are read-only. Dirty navigation requires confirmation; uncertain saves lock further writes until an exact current-file recheck or explicit discard.

From the `pi-workbench` root:

```bash
node apps/workbench-web/build.mjs
node --test apps/workbench-web/*.test.mjs packages/pi-web-integration/test/isolated-pi-web-stack.test.js
CHROME_BIN=/absolute/path/to/chromium node packages/pi-web-integration/scripts/run-workbench-chat-acceptance.mjs \
  --pi-web-root ../pi-web --owned-client-dist apps/workbench-web/dist
```

The browser check starts a separate fixture web/API, daemon and Chromium with isolated state, socket and ports. It seeds a pending question in the fixture daemon's memory and checks history, paging, answering, composer controls, draft reload, registered project/workspace/session navigation and new-session creation/reload, model/thinking option presentation, an isolated thinking-level mutation, three real extension dialogs opened by an owned fixture extension (confirm/select/input, reload, answer/cancel), image selection/rejection plus a real image prompt request, and persisted thought/tool messages added with the canonical Pi SessionManager before the isolated daemon starts. The browser checks tool/thinking structure and that embedded HTML cannot create elements or run script. It also seeds an isolated authoritative Workstream Store, checks the real plugin service projection of a checkpoint, Human Task and link, answers the task through the scoped service, verifies the resulting revision after refresh/reload, then resumes its confirmed session in the recorded workspace. Deterministic tests cover ambiguous answer outcomes, exact retry, stale revision and bounded roster validation. Browser roster projection injects a controlled activity payload into the isolated daemon's real status response, but does not yet prove an actual child/Worker execution. Files acceptance exercises real workspace reads, versioned saves, stale conflict, dirty navigation, inert untrusted text, bounded reads and backend traversal rejection. Independent Files security review and installed/native acceptance are outstanding. The credential-free fixture has no available models, so real model switching remains unproven (deterministic client tests cover the request/response seam). New empty sessions can be transient until a prompt persists them; reload validates the active session status. The Node tests cover simulated stream ordering, reconnect, gaps, send/stop responses and uncertain-create locking, model/thinking and queue validation, stale control replies and queue mutations; **the browser check accepts an image prompt at the real daemon but does not prove a model consumed it, produce a real model stream, test daemon restart or prove drafts across app restarts**. An ad-hoc Chat directory not matching exactly one registered workspace remains outside this slice; no catalog identity is invented. No live service is changed. The built assets under `dist/` have no PI WEB frontend-source import. See `NOTICE.md` for provenance and license.
